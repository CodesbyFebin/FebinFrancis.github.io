Game Architecture for Web: From Canvas to WebGL

Architectural patterns for web-based games and interactive experiences. Covers frame timing, input handling, state management, and performance optimization for interactive applications.

Published October 3, 2026 · Evidence-first technical note

Scope: This article explains engineering concepts and patterns. Repository source, tests and evidence remain authoritative for implementation claims.

Why this matters

Game loops are fundamentally different from request-response web applications. A game must render frames at 60 FPS, handle input in real-time, maintain consistent state and coordinate multiple systems (physics, AI, rendering) in sync. The architecture must support this without blocking or stuttering.

The game loop

Every frame:

  • Input: Poll keyboard, mouse, gamepad state.
  • Update: Apply physics, AI, game logic; modify entity positions and state.
  • Render: Draw current frame to canvas or WebGL context.

Use requestAnimationFrame to sync with display refresh (60 FPS @ 16.7ms per frame). Do not use setInterval; it's not synchronized.

State management

Separate concerns:

  • Game state: Positions, health, score, level data.
  • View state: Camera position, zoom, viewport.
  • Input state: Which keys are currently pressed (not just events).
  • Render state: Sprite atlases, shaders, textures already loaded.

Keep these orthogonal to enable testing, replaying and debugging.

Canvas vs. WebGL

Canvas 2D: Simple, immediate-mode drawing. Suitable for small scenes, UI, simple graphics. Slower for complex scenes.

WebGL: GPU-accelerated retained-mode rendering. Higher performance for complex 3D and large 2D scenes. Requires shaders and more setup.

Performance optimization

  • Limit draw calls: Batch similar objects to reduce GPU state changes.
  • Frustum culling: Don't render objects outside the visible camera area.
  • Object pooling: Reuse entity objects instead of creating/destroying them (garbage collection causes frame drops).
  • Sprite atlases: Use one large texture with many sprites instead of separate textures (faster than multiple draw calls).
  • Level of detail (LOD): Use simpler models or textures for distant objects.

Input handling

For smooth, responsive controls:

  • Track key state: Maintain a map of currently-pressed keys; update on keydown/keyup events.
  • Check state in update loop: Don't rely on individual events; they can be missed if update lags.
  • Gamepad API: Poll gamepad state manually; gamepad input doesn't fire events.
  • Pointer events: Use for mouse/touch input; handle both independently.

Frame timing and delta time

Frame rate varies. Update using delta time (elapsed since last frame) to ensure consistent motion:

position += velocity * deltaTime (not position += velocity)

Cap delta time to prevent huge jumps if a frame takes longer than expected.

Implementation checklist

  • Use requestAnimationFrame for the game loop.
  • Track key state; don't rely on events alone.
  • Use delta time for physics and movement.
  • Batch rendering to reduce draw calls.
  • Implement frustum culling to skip off-screen objects.
  • Use sprite atlases instead of separate textures.
  • Profile rendering time and optimize bottlenecks.

Verification

Test performance and responsiveness:

  • Frame rate under stress (many objects, complex physics).
  • Input latency (delay from key press to character movement on screen).
  • Memory usage (should be stable, not growing each frame).
  • Behavior at 30 FPS, 60 FPS, and variable frame rates.

Conclusion

Well-architected systems make constraints explicit, separate concerns, and design for failure. These principles apply across engineering disciplines — choose the right pattern for your problem, document assumptions, and verify through testing and evidence.
